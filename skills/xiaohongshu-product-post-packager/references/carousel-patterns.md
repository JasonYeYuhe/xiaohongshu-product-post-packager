# Carousel Patterns

## Default tutorial arc

1. **Hook** — what changed and why the reader should care
2. **Value** — what this enables in daily use
3. **Capability map** — 3–5 concrete things it can do
4. **Step 1** — where to start
5. **Step 2** — the only non-obvious hurdle
6. **Step 3** — what success looks like
7. **Caveats** — platform limits, account requirements, rollout notes
8. **Close** — save / try / compare / comment prompt

## Strong hook shapes

- “终于，X 可以 Y 了”
- “这个功能一开，X 的使用方式变了”
- “我把 X 的新功能跑通了，最值得记住的是这 4 步”
- “如果你经常在路上盯长任务，这个更新很有用”

## Caption pattern

1. One-sentence hook
2. One short paragraph on why it matters
3. Numbered steps
4. Caveats
5. One-sentence close
6. Hashtags

## Editing rules

- One idea per card
- Prefer concrete verbs over abstract praise
- Keep caveats factual, not apologetic
- If a sentence only exists to sound excited, cut it
- If a sentence saves the reader a mistake, keep it


## Method / workflow arc

Use when the post is about the user's operating method, personal system, or reusable workflow rather than a single product feature.

1. **Hook** — a sharp thesis or audience question
2. **Pain** — what breaks when the workflow is not systematized
3. **Mental model** — the new framing the reader should adopt
4. **Layer / step 1** — the first reproducible move
5. **Layer / step 2** — the key non-obvious mechanism
6. **Real artifact** — folder structure, code excerpt, settings panel, worklog, or output pack
7. **Validation** — how to test whether it actually works
8. **Payoff** — what becomes easier next time

## Audience-follow-up arc

Use when the user says a previous post got questions or someone asked for a tutorial.

1. **Cover** — “有朋友问：X 到底怎么做？”
2. **Clarify misconception** — what it is not
3. **Minimum viable version** — the smallest reproducible setup
4. **Critical trigger** — the one line/setting that matters most
5. **Workflow body** — what to write into the repeatable process
6. **Where complexity lives** — references/scripts/assets or equivalent
7. **Test with a real task** — proof it is not just theory
8. **Share / install / reuse** — if relevant
9. **Close** — experience becomes an asset

## Visual grounding rule

Avoid generic mock UI when the user has real artifacts. Prefer cleanly reconstructed panels based on actual files, commands, folder structures, logs, outputs, or screenshots. If a real screenshot is unsafe or illegible, reconstruct only the public-safe parts and keep the visual honest.
